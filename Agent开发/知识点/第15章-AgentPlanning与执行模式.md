# 第15章：Agent Planning 与执行模式

## ① 核心知识点

- **规划（Planning）**：把目标拆成步骤、依赖、输入输出和完成条件；规划不是最终事实，执行中必须允许修订。
- **ReAct**：思考（内部状态）与行动交替，适合路径未知、需即时观察的任务。
- **Plan-and-Execute**：先生成计划，再逐步执行并复盘；适合步骤较多且希望减少模型调用的任务。
- **Workflow/DAG**：开发者预定义节点和依赖，适合合规、可预测、高风险流程。
- **层级规划**：主管 Agent 分配子任务，子 Agent 在边界内执行；需限制深度、预算和权限。
- **并行/扇出**：独立子任务并行，汇聚节点统一校验；写操作要避免共享状态竞态。
- **计划契约**：每步包含 `step_id、输入、输出 schema、前置条件、风险级别、超时、回滚/补偿`。
- **选择原则**：不确定性越高用 Agent；风险和合规要求越高用 Workflow；多数企业采用混合模式。

## ② 原理

规划器输出候选计划，执行器按依赖调度，观察器把结果写入状态，重规划器在偏差、失败或新信息出现时修改剩余步骤。已完成且有副作用的步骤不可因重规划重复执行，必须复用幂等结果。

## ③ 企业架构

```text
目标解析 → 风险分类 → 规划器 → 计划校验器
                         ↓
                  工作流/DAG执行器
                   ↙      ↓      ↘
                工具网关  状态库  审批节点
                         ↓
                    评估与审计
```

- 计划校验器拒绝循环依赖、未知工具、越权步骤和超预算计划。
- 执行器支持串行、并行、超时、重试、暂停和恢复。
- 计划版本写入状态；重规划只修改未开始步骤，变更需记录原因。

## ④ 面试标准答案

> Planning 的价值是把复杂目标变成可验证的步骤，但计划不是可信事实。生产系统通常由 LLM 生成候选计划，再由规则校验器检查工具白名单、依赖、权限和预算，交给确定性工作流执行。路径未知用 ReAct，步骤稳定或高风险用 DAG/Workflow，长任务采用分阶段计划、检查点和失败后的局部重规划；副作用步骤必须幂等。

## ⑤ 高频追问

**Q：ReAct 和 Plan-and-Execute 怎么选？** 路径不确定且需即时反馈选 ReAct；步骤较多但结构清晰选先计划后执行；合规流程优先固定工作流。

**Q：计划失败是否整单重来？** 不应。保留已完成步骤，定位失败节点，查询其幂等状态后只重试或重规划剩余部分。

**Q：如何防止计划无限膨胀？** 限制最大步骤、深度、token、工具调用数和总耗时；达到预算直接暂停或转人工。

## ⑥ 场景题

**场景：供应商准入评估**

固定流程先收集材料、校验必填字段；Agent 仅负责从公开信息提取风险线索。高风险线索触发人工复核；并行查询互不依赖，最终由规则引擎计算分数，模型只能生成解释。

## ⑦ 生产事故题

**事故：重规划器把已付款步骤重新加入计划，重复扣款。**

- 根因：计划没有记录步骤状态和副作用边界，重规划覆盖了历史。
- 修复：步骤状态机 `PENDING/RUNNING/SUCCEEDED/FAILED` 持久化；重规划仅接受 `PENDING`；支付工具使用幂等键并先查单。
- 预防：计划变更 diff 审计、支付节点强制审批、回放测试覆盖“中途失败后重规划”。

## ⑧ 常见错误回答

- “有了 CoT 就等于规划。”——思维文本不具备可执行契约和状态。
- “计划越详细越可靠。”——过度细化增加 token 和脆弱依赖，应按风险拆分。
- “多 Agent 一定比单 Agent 强。”——通信和共享状态会增加故障面。
- “DAG 不能动态变化。”——可在边界内增补未开始节点，但必须版本化和审计。

## ⑨ Java/Python 实现思路

```python
plan = llm_plan(goal, schema=Plan)
validate_plan(plan, allowed_tools, budget)
for step in topo_sort(plan.steps):
    if state[step.id] != "PENDING":
        continue
    result = execute_step(step, idempotency_key=f"{run_id}:{step.id}")
    state[step.id] = "SUCCEEDED" if result.ok else "FAILED"
    checkpoint(state)
```

Java 可用 `enum StepStatus` + 持久化版本号实现乐观锁；依赖调度用现有工作流引擎，避免为单一场景自研 DAG。

## ⑩ 权衡与最佳实践

- 先确定性后智能化：能写成规则/工作流的步骤不要交给模型。
- 计划输出结构化、可校验、可 diff；自然语言只作为说明。
- 按风险分层规划：低风险自动化，高风险审批或人工执行。
- 计划、状态、工具版本绑定；重规划不得重放已成功副作用。
- 通过离线任务集评估计划成功率、步骤浪费率、重规划次数和成本。
