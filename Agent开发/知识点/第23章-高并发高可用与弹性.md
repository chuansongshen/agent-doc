# 第23章：高并发、高可用与弹性

## ① 核心知识点

- 先定 SLO：成功率、P95/P99 延迟、TTFT、并发会话数、每任务 token/cost。
- 令牌与请求是双重资源：同时受 QPS、TPM、上下文长度和连接数限制。
- 稳定性手段：超时、有限重试+指数退避抖动、熔断、舱壁隔离、限流、排队、过载保护。
- 弹性：无状态 API/Worker 水平扩展，队列削峰，HPA/KEDA 按 CPU、队列长度或自定义指标扩容。
- 高可用：多副本、就绪/存活探针、跨可用区、依赖降级、模型供应商故障转移。
- 一致性与副作用：幂等键、去重表、事务 outbox；读操作可重试，写操作需可证明不重复。

## ② 原理

- Little 定律：并发数 (L=吞吐量 λ×平均响应时间 W)。在目标吞吐固定时，延迟上升会直接推高并发和内存。
- 有界队列提供背压；队列满时按优先级拒绝、降级或返回 429，避免无限堆积导致雪崩。
- 熔断器状态 closed/open/half-open；连续失败或慢调用超过阈值后快速失败，冷却后探测恢复。
- 重试预算应小于总流量的固定比例（例如 10%），每次重试带随机抖动，避免惊群。
- HPA 是控制回路：采集指标→计算期望副本→滚动扩缩；扩容有冷启动延迟，需预热和最小副本。
- 多模型路由按延迟、价格、能力和配额选择；故障转移时保留上下文摘要并标记模型版本。

## ③ 企业架构

```text
客户端 → 全局流量/网关（鉴权、配额、限流）
      → 无状态 Agent API（超时、熔断、降级）
      → Redis/缓存 ─ 队列 ─ Worker 池（按租户/优先级隔离）
      → 模型路由层 → 多供应商/多区域模型
      → 状态库、幂等表、对象存储；Prometheus+OTel 监控
```

- API 与 Worker 分开扩容；长任务全部入队，短问答可同步但设置硬超时。
- 每租户配额（QPS、并发、token、费用）在网关和 Worker 双重执行，防止绕过。
- 关键依赖配置连接池上限、超时和舱壁；数据库使用读副本，写路径保持单一权威。
- K8s Deployment 多副本跨区，readiness 失败时摘流量，滚动升级保留快速回滚版本。
- 供应商故障按错误码分类：429 延迟重试，5xx 切换备用，策略不可恢复时转人工。

## ④ 面试标准答案

> 我先用 SLO 和容量模型确定目标并发，再把同步请求与长任务分离。入口做租户限流和幂等，运行时采用有界队列、超时、熔断、有限重试和舱壁隔离；Worker 无状态化，通过 HPA/KEDA 按队列和延迟扩缩。模型调用有多供应商路由和降级答案，写操作使用 outbox/去重保证不重复。通过 Prometheus 指标和 OpenTelemetry trace 验证扩容、故障转移和回滚，确保在峰值及单依赖故障下仍满足 SLO。

## ⑤ 高频追问

- **为什么只看 CPU 扩容不够？** LLM 服务常被队列长度、token 或外部限额限制，应使用自定义业务指标。
- **重试几次合适？** 以端到端预算反推，通常 1～2 次；每次退避+抖动，并设置总超时和重试预算。
- **如何防止单租户拖垮系统？** 网关配额、租户独立队列/并发池、费用熔断和优先级调度。
- **模型故障切换会影响质量吗？** 会，记录模型版本，必要时降低功能或转人工，不可静默改变高风险决策。
- **何时用缓存？** 仅对可复用且不含敏感实时数据的结果缓存，键包含模型、提示版本和权限摘要。

## ⑥ 场景题

**场景：** 月末报销助手并发从 200 升到 2000，模型供应商限额不变。

**解法：** 入口按租户限流，短请求超额返回排队凭证；任务进入有界队列，Worker 依据 TPM 配额调度；常见政策问答走版本化缓存，附件解析异步化；达到队列水位触发降级（仅返回规则链接）和扩容；监控排队时长与 429，保证核心财务租户优先。

## ⑦ 生产事故题

**事故：** 上线新模型后 P99 从 8 秒升至 40 秒，重试流量进一步放大，数据库连接耗尽。

**处理：** 先冻结发布并关闭自动重试，熔断新模型、切备用模型；降低入口并发和队列上限，恢复数据库连接。通过 trace 定位为模型延迟上升而非数据库慢；修复重试预算、连接池和超时配置，压测验证后分批放量。

## ⑧ 常见错误回答

- “加机器就能解决高并发。”——忽略模型配额、队列和下游瓶颈。
- “失败就重试三次。”——可能产生指数级流量和重复副作用。
- “熔断会降低可用性，所以不用。”——快速失败和降级通常优于线程耗尽。
- “HPA 只看 CPU。”——Agent 关键容量是 token、队列和端到端延迟。
- “多活就是复制数据库。”——还需会话粘性、幂等、时钟与故障切换演练。

## ⑨ Java/Python 实现思路

Python（有界并发+超时）：

```python
import asyncio

sem = asyncio.Semaphore(100)  # 每实例并发上限

async def call_model(req):
    async with sem:
        try:
            return await asyncio.wait_for(provider(req), timeout=8)
        except asyncio.TimeoutError:
            raise ServiceUnavailable("model timeout")
```

Java：使用 Resilience4j `TimeLimiter + CircuitBreaker + Bulkhead + Retry` 组合；队列用 Kafka/RabbitMQ，消费者并发受租户配额限制，数据库以唯一幂等键约束重复写入。

## ⑩ 权衡与最佳实践

- 队列提高吞吐但增加等待；为交互请求设最大排队时长，超时即降级或转人工。
- 多供应商提高可用性但带来质量、合规和成本差异；路由策略需可配置、可审计、可回滚。
- 全局限流简单但不公平；企业场景优先租户/用户/工具多级配额。
- 扩容前先压测冷启动、连接池和模型限额；设置最小副本、预热和优雅终止。
- 所有 SLO、阈值和降级文案纳入版本控制，定期做单依赖故障演练。
