# 第11章：Function Calling / Tool Calling

## ① 核心知识点

- **定义**：模型返回结构化工具意图（工具名、参数、`call_id`），由运行时校验、鉴权、执行并把结果回传；模型本身不直接执行副作用。
- **Schema**：使用 JSON Schema 描述参数；字段类型、必填项、枚举、范围和示例要明确。支持时启用 `strict`，仍需服务端二次校验。
- **生命周期**：`用户请求 → 模型决策 → 工具调用 → 参数校验/授权 → 执行 → 工具结果 → 模型继续或结束`。
- **工具分类**：查询类（只读）、变更类（有副作用）、长任务类（异步）、组合类（内部再编排）。按风险分级而非按技术名称分级。
- **并行调用**：相互独立的只读调用可并行；有顺序依赖、共享资源或副作用时必须串行。
- **边界规则**：调用超时必须可取消；重试只针对可重试错误；有副作用的工具必须带幂等键；未知字段默认拒绝。
- **安全**：工具白名单、租户隔离、最小权限、敏感参数脱敏、审计日志、提示注入防护。
- **可观测性**：记录模型版本、提示版本、工具版本、参数摘要、延迟、结果状态和 `trace_id`，禁止记录明文密钥。

## ② 原理

1. 模型根据工具描述生成调用意图，不保证业务语义正确。
2. 运行时把意图解析为内部命令：`{call_id, name, args, actor, deadline}`。
3. Schema 校验解决“格式正确”，业务校验解决“数据存在、权限足够、状态允许”。
4. 执行器在独立进程/沙箱中调用真实服务，返回稳定的结果协议：`ok | retryable_error | terminal_error`。
5. 运行时把结果按原 `call_id` 关联回模型；模型可继续调用、改参重试或给出最终答复。

**幂等判定**：同一 `idempotency_key` 的请求只能产生一次业务效果；网络超时后重试必须查询原请求状态，不能盲目再次扣款/发货。

## ③ 企业架构

```text
客户端/API
  → Agent Runtime（循环、预算、上下文）
  → Tool Gateway（Schema、鉴权、限流、审计）
  → Tool Adapter（ERP/CRM/数据库/消息队列）
  → 结果归一化与状态存储
```

- **工具注册中心**：名称、版本、Schema、风险级别、负责人、SLO、弃用日期。
- **策略层**：按租户、用户、数据域和风险级别决定允许/审批/拒绝。
- **执行层**：短调用同步返回；长调用返回 `job_id`，通过轮询或事件回调完成。
- **状态层**：保存 `call_id`、幂等键、请求摘要、结果引用和重试次数，支持恢复。
- **治理**：契约测试、金丝雀发布、工具版本锁定、全链路 Trace 与成本指标。

## ④ 面试标准答案

> Function Calling 是模型输出结构化动作意图的协议，不是执行引擎。企业实现要把模型输出当作不可信输入，在运行时做 Schema 与业务校验、权限和风险审批，再由具备超时、幂等、重试、审计能力的工具网关执行。执行结果按 `call_id` 回传，Agent 根据结果继续或终止。只读工具可并行，有副作用工具必须幂等并默认串行。

## ⑤ 高频追问

**Q：`strict` 能否替代参数校验？** 不能；它约束结构，不检查资源存在性、权限和业务状态。

**Q：模型重复调用怎么办？** 以业务键生成幂等键，在网关去重；返回第一次结果，不依赖模型“自觉”。

**Q：工具结果应返回多少？** 返回完成下一步所需的最小字段，长内容用对象存储引用，避免上下文膨胀和敏感信息泄露。

**Q：何时允许并行？** 仅当调用相互独立、无写冲突、结果合并顺序不影响业务；否则串行或由工作流编排。

## ⑥ 场景题

**场景：客服查询订单并申请退款**

1. `get_order`（只读）确认订单、支付状态和可退金额。
2. 退款金额超过 5000 元或高风险账户，进入审批；否则生成 `refund_order` 调用。
3. `refund_order` 使用 `refund:{order_id}:{request_id}` 幂等键，超时后先查退款状态。
4. 成功后回传退款单号；失败则区分可重试与需人工处理。

## ⑦ 生产事故题

**事故：退款接口超时，Agent 重试导致重复退款。**

- 根因：把网络超时当作“未执行”，没有幂等键和状态查询。
- 处置：立即暂停该工具；按请求号查询支付渠道；对账并人工冲正；保留完整审计轨迹。
- 修复：网关强制幂等键；超时状态设为 `UNKNOWN`，先查询再决定；副作用工具默认最多一次业务提交，重试仅查询。

## ⑧ 常见错误回答

- “模型能直接调用数据库。”——模型只能提出意图，数据库访问必须经过受控服务。
- “Schema 正确就一定安全。”——仍可能越权、注入或操作错误租户。
- “所有工具都可以并行提升速度。”——写操作会产生竞态和重复副作用。
- “失败统一重试三次。”——4xx、权限、参数错误通常不可重试；应按错误分类和预算重试。

## ⑨ Java/Python 实现思路

```python
def dispatch(call, actor, deadline):
    schema_validate(call["arguments"])
    authorize(actor, call["name"])
    key = call["arguments"].get("idempotency_key")
    if is_side_effect(call["name"]) and not key:
        raise ValueError("副作用工具必须提供幂等键")
    return tool_gateway.execute(call["name"], call["arguments"], deadline, key)
```

Java 中用 `record ToolCall(String callId, String name, JsonNode args)` 表示调用；网关统一执行 `validator → policy → executor`，超时用 `CompletableFuture.orTimeout`，结果写入审计表后再回传模型。

## ⑩ 权衡与最佳实践

- 工具少而清晰优于“大而全”；每个工具只做一件可审计的事。
- Schema 与业务规则分层；服务端永远不信任模型参数。
- 默认最小权限、默认拒绝未知工具；高风险动作先审批。
- 只读调用可并行，副作用调用串行并使用幂等键；重试采用指数退避并设置总截止时间。
- 结果最小化、敏感字段脱敏、版本锁定；上线前做契约和回放测试。
