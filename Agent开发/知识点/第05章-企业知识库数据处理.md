# 第05章：企业知识库数据处理

## ① 核心知识点

- 数据处理决定 RAG 上限：采集、解析、清洗、切分、元数据、权限、去重和质量门禁缺一不可。
- 支持 PDF/Office/HTML/表格/图片/OCR；保留标题层级、页码、表格关系和原文链接，不能只存纯文本。
- 每个文档建立 `doc_id、source_uri、content_hash、version、owner、acl、effective_time、status`。
- 清洗只去格式噪声，不改业务含义；敏感信息脱敏需可配置并记录审计。
- 失败文件进入隔离队列，人工修复后可重放；原文和派生文本都要可追溯。

## ② 原理

把知识库看作可重放 ETL：`Extract → Normalize → Enrich → Quality Gate → Publish`。解析阶段按 MIME 和版式选择工具，OCR 输出置信度；规范化统一编码、空白、日期和术语，但保留原文快照。内容哈希用于幂等和变更检测，文档版本与生效时间用于回答“当时有效的政策”。质量门禁检查空文本、异常字符、页数突变、重复率和 ACL 缺失，未通过的数据不进入线上索引。

## ③ 企业架构

```text
数据源(S3/SharePoint/DB) → 连接器/增量游标 → 解析与OCR集群
      → 清洗/结构化/PII检测 → 元数据与ACL服务 → 对象存储原文
      → Chunk/Embedding队列 → 向量库+关键词索引 → 发布清单
```

采用事件总线传递 `document.changed/deleted`；处理器按 `content_hash+pipeline_version` 幂等。原文写入不可变存储，派生结果写入版本目录；发布通过原子别名切换，避免半批数据可见。监控处理延迟、失败率、OCR 置信度和待处理积压。

## ④ 面试标准答案

> 企业知识库不是“把文件转成向量”，而是一条可追溯、可增量、可回滚的数据流水线。我们保留原文和版本，解析时维护结构和页码，清洗与 PII 检测后做质量门禁，再生成带 ACL 的 chunk 和 embedding。通过内容哈希实现幂等，失败隔离、可重放，最后用原子发布保证线上一致性。

## ⑤ 高频追问

1. **扫描 PDF 怎么办？** 先版面检测，按页 OCR；低置信度或表格错位进入人工复核，不直接上线。
2. **如何判断文档变更？** 比较规范化文本哈希和来源更新时间；内容未变只更新权限等元数据。
3. **为什么保留页码？** 便于引用、人工核对和事故追溯；前端展示必须能定位到原文。
4. **如何处理重复文档？** 精确哈希去重，近似重复用 SimHash/MinHash 标记，保留权威来源并记录映射。

## ⑥ 场景题

**场景：HR 政策库。** 每晚扫描网盘增量文件，先解析 DOCX/PDF，再提取部门、生效日期和访问组。过期政策不删除而标记 `status=expired`，检索默认过滤；新政策通过抽样问答集验证后切换别名。员工只能检索所属区域，引用必须显示文件名、版本和页码。

## ⑦ 生产事故题

**事故：OCR 把“不得”识别成“得”，导致错误报销。** 立即将该批文档下线并回滚别名，通知业务暂停自动审批；从原图重跑高精度 OCR，增加否定词/金额字段校验和低置信度阈值；对关键政策要求人工双审。验证：抽样 500 页字符准确率≥99%，关键字段零错误后再发布。

## ⑧ 常见错误回答

- “解析失败的文件跳过就行”——会形成知识盲区，必须告警并可重放。
- “清洗时把页眉页脚和编号全删掉”——可能破坏条款语义和引用位置。
- “只存最新版本，旧文件可丢弃”——无法回答历史时点，也无法审计。
- “ACL 在前端过滤即可”——前端不可信，必须在检索服务/数据库强制执行。

## ⑨ Java/Python 实现思路

```python
def ingest(file):
    raw = object_store.put_immutable(file.bytes)
    parsed = parse_by_mime(file.mime, file.bytes)      # 失败抛出并进隔离队列
    text = normalize(parsed.text)
    meta = {"doc_id": file.id, "hash": sha256(text), "version": next_version(file.id),
            "acl": load_acl(file.id), "source": file.uri}
    quality_gate(text, meta, parsed.ocr_confidence)
    publish_queue.put({"raw": raw, "text": text, "meta": meta})
```

Java 可用 Apache Tika 识别类型、PDFBox 解析 PDF，消息队列承载重试；所有处理器记录 `pipeline_version` 和 `trace_id`，异常写入死信队列。

## ⑩ 权衡与最佳实践

- 高精度 OCR 成本高；仅对扫描件或低置信度页启用，文本型 PDF 走快速解析。
- 全量重建简单但耗时；增量处理需维护游标、幂等和删除事件，适合生产。
- 清洗越激进，噪声越少但语义风险越大；保留原文快照与可逆处理记录。
- 先做数据质量和权限门禁，再谈模型升级；垃圾进，垃圾出。
