# 第30章：Observability 与线上排障

## ① 核心知识点

- 三件套：Trace 还原一次任务的模型/检索/工具链路，Metrics 看趋势与 SLO，Logs 记录可检索事件与决策摘要。
- 统一关联键：`trace_id、task_id、tenant_id、agent_version、model、prompt_version、tool_name`。
- GenAI 指标：请求数、成功/错误率、TTFT、总时延、输入/输出 token、缓存命中率、工具耗时/错误、重试次数、成本。
- SLO 示例：任务成功率 ≥99%，P95 总时延 ≤8 s，P95 TTFT ≤1.5 s，工具错误率 ≤0.5%，安全违规率=0。
- 高基数字段（完整 prompt、用户 ID）不直接做 Prometheus label；使用 trace/log 关联并脱敏。
- 排障遵循“现象→范围→时间线→依赖分解→最小修复→回归验证”，先止损再定位。

## ② 原理

- Trace 是有向树：`agent.run` 父 span 下挂 `llm.generate`、`retrieval.query`、`tool.call`；每个 span 带开始/结束时间和状态。
- RED（Rate、Errors、Duration）衡量服务；USE（Utilization、Saturation、Errors）衡量资源；二者结合定位瓶颈。
- 直方图计算 P50/P95/P99；计数器只增不减，仪表盘避免把平均延迟当 SLO。
- 采样策略：正常流量低比例头采样，错误/高延迟/高风险任务尾采样；敏感内容默认不入 span 属性。
- 线上诊断优先对比基线：按版本、模型、租户、工具和区域切片，找出首次异常时间与共同维度。
- 事件响应分级：P0 数据/资金风险立即停用工具；P1 SLO 大面积回退限流/回滚；P2 局部降级并排期修复。

## ③ 企业架构

```text
Agent SDK/网关埋点 → OTel Collector → Trace 后端
                  ├→ Prometheus（指标）→ 告警/看板
                  └→ 日志管道（脱敏）→ SIEM/检索
任务与版本元数据 ───────────────┘
```

- 在运行时中间件统一埋点，工具开发者只提供业务字段，避免各团队自定义命名。
- OTel Collector 做批处理、采样、脱敏和多后端导出；失败时本地有界队列，不能阻塞主链路。
- 告警采用多窗口燃烧率（例如 5 分钟/1 小时）+ 业务阈值，通知包含 runbook 和回滚开关。
- 看板分四层：业务成功、Agent 轨迹、模型/工具依赖、基础设施；每层都可点击跳转 trace。
- 变更平台写入 `deployment_id`，实现发布前后自动对比；审计日志单独存储并限制访问。

## ④ 面试标准答案

> 我用 OpenTelemetry 统一采集 Agent、模型、检索和工具 span，用 Prometheus 记录 RED、token、成本和业务成功率，日志只保留脱敏摘要并通过 trace_id 关联。SLO 以成功率、P95 时延和 TTFT 为核心，告警按版本/模型/租户切片并配 runbook。线上异常先限流、降级或回滚止损，再沿 trace 找首次失败依赖，结合指标和日志确认根因，修复后用同一 trace 与回放样本验证。

## ⑤ 高频追问

- **为什么不用只打日志？** 日志难聚合趋势，Trace 无法看总体 SLO；三件套需关联而非互替。
- **如何控制可观测成本？** 采样、字段白名单、聚合 token 指标；错误和高风险请求提高采样率。
- **Prompt 能否放 trace？** 默认不放原文，使用哈希/模板版本和脱敏摘要，按合规授权短期留存。
- **P95 突增先看哪里？** 先按时间和版本切片，再看 span 分解：模型、检索、工具、排队或网络。
- **指标告警如何避免噪声？** 采用多窗口燃烧率、最小样本量和抑制重复告警，绑定明确行动。

## ⑥ 场景题

**场景：** 客服 Agent 偶发回答变慢，平均时延正常。

**解法：** 看 P99/P95 及尾部 trace，按模型和工具切片；发现少数检索 span 超过 3 秒。检查向量库慢查询和索引版本，临时限制 top-k、启用缓存并扩容；修复索引后用同样查询回放，确认 P95 恢复且答案质量未降。

## ⑦ 生产事故题

**事故：** 夜间成本告警，单租户 token 用量飙升 20 倍。

**排查：** Prometheus 按租户 token counter 定位，trace 显示工具返回超大文档导致上下文膨胀；日志确认新工具版本未限制响应大小。立即暂停该工具、设置响应截断和租户预算，清理异常任务；补充 `tool.response_bytes`、token/任务和成本/任务告警，灰度验证后恢复。

## ⑧ 常见错误回答

- “有日志就能排障。”——没有跨服务关联和时间线仍会迷路。
- “所有字段都做指标标签。”——高基数会拖垮时序数据库并泄露隐私。
- “只看平均延迟。”——尾延迟决定用户体验和容量。
- “先优化模型。”——应先用 trace 证明瓶颈，可能是排队、网络或工具。
- “告警越多越可靠。”——无行动的噪声会导致值班人员忽略真正事故。

## ⑨ Java/Python 实现思路

Python（OpenTelemetry 最小 span）：

```python
from opentelemetry import trace
tracer = trace.get_tracer("agent")

with tracer.start_as_current_span("tool.call") as span:
    span.set_attribute("gen_ai.tool.name", "order.read")
    result = call_tool()
    span.set_attribute("tool.status", "ok")
```

Java：使用 OpenTelemetry Java Agent 自动采集 HTTP/DB，业务代码用 `Tracer.spanBuilder("tool.call")`；Micrometer/Prometheus 暴露计数器和直方图，MDC 写入 `trace_id`，日志通过 JSON 且字段白名单化。

## ⑩ 权衡与最佳实践

- 全量 trace 便于复盘但成本和隐私风险高；采用错误/高延迟/高风险优先采样。
- 高粒度指标利于切片但增加存储；固定核心标签，细节放 trace/log。
- 自动修复（如切模型）恢复快但可能掩盖根因；动作需限时、可回滚并记录审计。
- 业务质量指标与基础设施指标必须同一时间轴，避免“服务健康但答案错误”的盲区。
- 每个告警都配一页 runbook：症状、查询、止损开关、升级联系人和验证命令。
