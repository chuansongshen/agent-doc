# 第27章：Agent Security

## ① 核心知识点

- 信任边界：模型输出、检索内容、工具描述和用户输入均视为不可信数据；策略代码才是最终裁决者。
- OWASP GenAI LLM Top 10 重点风险：提示注入、敏感信息泄露、供应链、数据/模型投毒、不当输出处理、过度代理权限、系统提示泄露、向量/嵌入弱点、错误信息、资源失控。
- 身份与权限：用户身份、Agent 身份、工具服务身份分离；最小权限、短期令牌、按资源/动作授权。
- 工具安全：明确 schema、参数白名单、输入输出校验、幂等、沙箱、网络出口限制和人工审批。
- 数据安全：租户隔离、传输/存储加密、脱敏/DLP、最小上下文、保留期限和可审计访问。
- 生命周期：威胁建模→安全评测/红队→发布门禁→运行监控→事件响应；按 NIST AI RMF 的 Govern、Map、Measure、Manage 闭环。

## ② 原理

- **直接提示注入**来自用户；**间接注入**藏在网页、邮件、文档或工具返回值中。把外部内容放入明确的数据区，禁止其改变系统策略。
- Agent 容易形成“困惑代理”：模型持有高权限凭证，被诱导执行越权操作。通过能力令牌（capability token）绑定用户、资源、动作、过期时间。
- 输出不是代码：结构化解析后仍需业务规则校验（金额、SQL、URL、收件人），拒绝未知字段和危险组合。
- 纵深防御：输入过滤只能减风险，不能替代权限、沙箱、人工确认和审计；任何一层失效都不应造成不可逆损害。
- 供应链风险覆盖模型、提示模板、向量库、MCP/插件和依赖包；固定版本、签名校验、SBOM 和变更审批。
- 安全事件以证据链为中心：保存 prompt/工具调用摘要、策略决策、身份、版本和时间戳，同时脱敏个人数据。

## ③ 企业架构

```text
用户/应用 → API 网关（认证、租户、速率）
          → Policy Engine（RBAC/ABAC、风险分级、审批）
          → Agent Runtime（模型与上下文隔离）
          → Tool Gateway → 细粒度服务账号/沙箱
          ├─ DLP/内容安全/输出校验
          ├─ 审计日志与 SIEM
          └─ 向量库/记忆库（租户分区、加密、ACL）
```

- 高风险动作（付款、删除、外发邮件、生产变更）默认“计划→预览→用户确认→执行”。
- 工具网关统一做 schema 校验、配额、超时、出站域名白名单和响应大小限制，禁止模型直连内网。
- Secrets Manager 只在工具进程短时注入凭证，提示词、日志和向量库不得持久化密钥。
- 每次调用带 `principal_id、tenant_id、purpose、policy_version、trace_id`，审计日志防篡改并设置保留期。
- 红队样本和安全回归集进入 CI；策略、模型、工具版本任一变化都触发评测。

## ④ 面试标准答案

> 我把 Agent 当作不可信的决策组件，采用 OWASP 风险清单和 NIST AI RMF 做威胁建模。权限上实行用户、Agent、工具三种身份分离和最小权限，短期能力令牌绑定资源与动作；工具经过网关 schema/业务校验、沙箱和出站白名单，高风险操作必须人工确认。对提示注入、数据泄露、供应链和资源滥用做红队回归，所有决策以脱敏审计日志留痕，并准备撤销令牌、熔断工具和人工接管的应急开关。

## ⑤ 高频追问

- **系统提示加一句“不要泄露”够安全吗？** 不够，提示是可被诱导的；必须依赖权限、DLP 和输出校验。
- **RAG 文档可信就不用过滤？** 文档可能被投毒或包含间接注入，需来源校验、分区 ACL 和内容扫描。
- **为什么不给 Agent 一个管理员账号？** 过度权限会把模型错误放大为数据或资金事故。
- **如何防止 SSRF/内网探测？** URL 解析后只允许 HTTPS 和域名白名单，解析 IP 禁止私网/环回，工具运行在受限网络。
- **日志记录完整 prompt 吗？** 生产默认脱敏/哈希和最小摘要；仅在合规授权的隔离环境短期保留原文。

## ⑥ 场景题

**场景：** 客服 Agent 可查询订单并发起退款，用户输入和订单备注都可被攻击者控制。

**解法：** 订单备注当作不可信数据，放入独立上下文；退款工具只接受订单号和金额，服务端重新查询实付金额并校验额度；超过阈值需人工审批；令牌绑定当前用户和订单，调用全量审计，失败自动撤销并告警。

## ⑦ 生产事故题

**事故：** Agent 读取恶意网页后调用邮件工具，将内部客户名单发送到外部地址。

**处置：** 立即停用外发工具并撤销相关令牌，隔离任务和网络出口；从审计 trace 重建注入链路和泄露范围，通知安全/合规。修复为收件人域名白名单、外发人工确认、DLP 扫描和网页内容数据标记；用同类 payload 做回归和灰度验证。

## ⑧ 常见错误回答

- “把温度调低就安全。”——随机性与越权不是同一问题。
- “只做输入关键词过滤。”——无法覆盖编码、间接注入和工具返回值。
- “工具权限由模型自己决定。”——权限必须由策略引擎和服务端强制执行。
- “所有日志永久保存方便追责。”——违反最小化、隐私和合规要求。
- “安全策略上线后不用再测。”——模型、数据、工具和提示变化都会改变攻击面。

## ⑨ Java/Python 实现思路

Python（工具白名单与参数校验）：

```python
ALLOWED = {"order.read": "orders:read", "refund.create": "orders:refund"}

def authorize(principal, tool, args):
    scope = ALLOWED.get(tool)
    if not scope or scope not in principal.scopes:
        raise PermissionError("tool denied")
    if tool == "refund.create" and args["amount"] > 5000:
        raise PermissionError("human approval required")
    return run_tool(tool, sanitize(args), timeout=5)
```

Java：Spring Security `AuthorizationManager` 做 RBAC/ABAC，Jackson `JsonSchema` 严格反序列化，工具进程使用容器 seccomp、只读文件系统和 NetworkPolicy；高风险接口以数据库唯一键实现幂等。

## ⑩ 权衡与最佳实践

- 过滤越严误报越多；高风险动作宁可转人工，低风险问答可采用抽样审核和速率限制。
- 沙箱提升隔离但增加延迟和运维成本；按工具风险分级，不必所有只读查询都启用重型隔离。
- 细粒度策略带来配置复杂度；策略版本化、默认拒绝并提供可解释的拒绝原因。
- 记忆越丰富越个性化，也越易泄露/投毒；只保存必要事实并设置过期、删除和来源标记。
- 每季度做提示注入、越权、数据泄露和供应链演练，确保“停用工具/撤销令牌/人工接管”可在分钟级生效。
