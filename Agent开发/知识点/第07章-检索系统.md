# 第07章：检索系统

## ① 核心知识点

- 检索目标是高召回地找全证据，再以精确排序提供少量上下文；不要让生成模型承担检索。
- 查询处理：意图/语言识别、改写、同义词、拼写纠错、过滤条件抽取；保留原查询以便审计。
- 召回策略：dense 语义、BM25 关键词、metadata 过滤、时间/权限过滤；混合结果用 RRF 或加权融合。
- Reranker 对候选 query-document 做交叉编码，提升精度但增加延迟；设置 topK、分数阈值和去重。
- 结果必须带来源、版本、页码和权限；无足够证据时返回“不确定”而不是编造。

## ② 原理

两阶段排序：第一阶段 ANN/BM25 取 topN（强调 Recall），第二阶段 reranker 计算相关性取 topK（强调 Precision）。RRF 常用 `score=Σ1/(k+rank)`，无需不同分数归一化。查询改写可生成多个子查询，但必须限制数量并与原问题合并，防止语义漂移。MMR 通过 `λ·sim(query,doc)-(1-λ)·max sim(doc,selected)` 兼顾相关性和多样性。过滤应尽量下推到索引层，避免先取结果再在应用层删掉导致召回不足。

## ③ 企业架构

```text
Query API → 意图/改写 → ACL与结构化过滤
                    ├→ BM25 topN ─┐
                    └→ Dense topN ─┼→ RRF/加权 → Reranker → 去重/阈值
                                   └→ 引用拼装 → LLM
```

检索服务独立扩展，缓存规范化查询和热门结果（缓存键含租户、权限、索引版本）。记录每阶段耗时、候选数、分数分布和最终引用；超时时降级为 BM25 或较小 topK。索引更新通过版本别名，保证查询读到一致快照。

## ④ 面试标准答案

> 检索系统采用“召回—融合—重排”架构：dense 捕获语义，BM25 保留编号和专有名词，metadata/ACL 先过滤；RRF 合并候选，reranker 精排后按阈值和多样性截断。通过 Recall@K、MRR/nDCG、引用准确率、p95 延迟和成本评估，证据不足就拒答或转人工。查询改写必须可回放、限次数并保留原意。

## ⑤ 高频追问

1. **为什么不用纯向量？** 对精确术语、数字、版本号不敏感，混合检索更稳。
2. **Reranker 放哪？** 只处理 topN 候选；N 太小损失召回，太大增加延迟，需用评测找拐点。
3. **分数阈值如何定？** 在标注集按租户/意图校准，监控分数漂移，不能跨模型直接比较。
4. **多轮问题如何检索？** 先把代词补全为独立查询，再保留会话过滤条件；改写失败回退原问题。

## ⑥ 场景题

**场景：IT 工单助手。** 解析“上周华东区支付超时”得到时间、区域、产品过滤；BM25 查错误码，dense 查现象描述，合并后 rerank。只返回用户有权限的工单，引用工单号和时间。若 top3 分数均低于阈值，提示补充信息并转人工，而不是生成推测原因。

## ⑦ 生产事故题

**事故：上线同义词扩展后结果被营销文档淹没。** 监控发现 BM25 召回量暴涨、nDCG 下降。回滚词典并按业务字段限定扩展；增加“产品/版本/错误码”字段权重和文档类型过滤；对高频查询建立金丝雀集。验证：核心意图 nDCG@10 恢复基线，p95 延迟不超过预算。

## ⑧ 常见错误回答

- “topK 取 3 就够了”——不同问题所需证据量不同，应评测和动态截断。
- “先查全库再做权限过滤”——会泄露候选标题和造成召回错误，权限必须前置/下推。
- “改写越多越全面”——可能引入错误意图和成本，限制候选数并与原查询对照。
- “检索分数高就直接回答”——必须检查来源版本、冲突和证据完整性。

## ⑨ Java/Python 实现思路

```python
q = normalize(user_query)
filters = extract_filters(q, user_acl)
dense = vector_store.search(embed(q), k=50, filter=filters)
sparse = bm25.search(q, k=50, filter=filters)
candidates = rrf_merge(dense, sparse, k=60)
ranked = reranker.rank(q, dedupe(candidates)[:80])[:8]
return [h for h in ranked if h.score >= threshold_for(q.intent)]
```

Java 侧将 `Retriever`、`Reranker` 定义为少量稳定接口，使用 CompletableFuture 并行 dense/BM25；设置总超时，任一路失败仍可返回另一条结果并打降级标记。

## ⑩ 权衡与最佳实践

- 纯 dense 最简单；混合+rerank 质量高但运维和延迟增加，先用离线数据证明增益。
- 查询改写适合口语和多轮问题；对编号/SQL 等精确查询应关闭或保留原词。
- 缓存能降成本但会带来权限和版本陈旧风险，缓存键必须含身份范围和索引版本。
- 统一返回 `evidence_id` 和可点击引用，生成层只消费白名单证据。
