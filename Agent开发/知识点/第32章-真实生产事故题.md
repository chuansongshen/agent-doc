# 第32章：真实生产事故题

## ① 核心知识点

- 事故题考察止损优先、证据链、根因分析、修复验证和防复发，而不是背某个模型名称。
- Agent 常见事故：提示/数据间接注入、越权或跨租户泄露、工具重复副作用、无限循环与费用失控、供应商限流、检索索引错误、流式连接堆积。
- 统一严重度：P0（资金/隐私/安全）、P1（大面积不可用或 SLO 破坏）、P2（局部质量/性能）。
- 关键控制：kill switch、令牌撤销、工具熔断、租户限流、只读降级、人工接管、版本回滚和数据恢复。
- 证据最小集：trace/task_id、模型/提示/工具版本、输入输出摘要、权限决策、时间线、影响范围和变更记录。
- 复盘要求：5 Whys/故障树、触发条件、检测延迟、修复项负责人和截止时间；不归咎个人。

## ② 原理

- 事故响应四阶段：准备（runbook/演练）→检测与分析→遏制/根除/恢复→事后活动（复盘、指标、改进）。
- 先隔离“能力”再处理“数据”：关闭高风险工具和外部出口，撤销短期凭证，保留只读查询，避免边查边扩大损害。
- 用时间线区分触发、放大器和根因：例如模型变慢是触发，盲目重试是放大器，缺少预算/熔断是系统根因。
- 影响评估按租户、记录数、金额、时长和法规时限量化；不确定部分标注估计区间。
- 恢复采用分阶段：回滚版本→小流量验证→逐步放量；任何数据修复都先备份并可逆。
- 事故指标：MTTD、MTTR、受影响任务数、错误/泄露量、检测覆盖率、回归通过率。

## ③ 企业架构

```text
告警/用户报告 → 值班响应（分级、建 war room）
      ├→ Kill Switch/策略中心（停工具、撤销令牌、限流）
      ├→ Trace/日志/审计取证
      ├→ 配置与版本仓库（回滚、冻结发布）
      ├→ 数据与合规评估（通知、取证保全）
      └→ 修复验证/灰度 → 复盘与改进项跟踪
```

- 策略中心必须高可用且可在分钟级生效，默认安全配置在其不可用时拒绝高风险动作。
- 运行时设置全局、租户、工具三级预算（请求、token、金额、时长），触顶自动熔断。
- 审计日志写入防篡改存储；敏感原文隔离并按合规授权访问，避免二次泄露。
- 回滚包同时包含模型、提示、工具 schema、策略和索引版本，禁止只回滚代码。
- 每季度演练注入、供应商中断、数据库故障和密钥泄露，记录实测 MTTD/MTTR。

## ④ 面试标准答案

> 遇到 Agent 事故我先按 P0/P1/P2 分级并止损：停用高风险工具、撤销令牌、限流或切只读/备用模型；随后用 trace、审计和版本信息建立时间线，区分触发、放大器和根因，量化受影响租户与数据。修复采用可回滚变更和小流量验证，确认质量与安全指标恢复后再放量。最后做无责复盘，补齐预算、幂等、权限、监控和回归测试，并跟踪负责人和截止日期。

## ⑤ 高频追问

- **用户说“数据泄露”但没有日志怎么办？** 先按最坏情况隔离和保全现有证据，依据访问日志/网络流量估算范围，并补齐审计。
- **什么时候回滚，什么时候修配置？** 影响面大或根因不明先回滚；可证明配置错误且风险可控时热修，但保留回滚点。
- **如何证明没有重复扣款？** 以业务幂等键和交易流水核对，不以 Agent 日志次数推断。
- **事故中能继续收集 prompt 吗？** 仅收集脱敏摘要和哈希，遵守最小化和合规，原文需授权隔离。
- **复盘如何避免“加监控”式空泛措施？** 每项改进绑定可验证指标、负责人、截止时间和演练场景。

## ⑥ 场景题

**场景：** 供应商返回 429，Agent 重试导致队列堆积，用户全部超时。

**解法：** 立即降低入口并发、暂停非核心任务，切换备用模型或规则答案；设置按供应商的令牌桶、重试预算和抖动，队列满时返回排队凭证；恢复后分批重放幂等任务，核对成功率、P95 和积压清零时间。

## ⑦ 生产事故题

**事故 A（间接注入）：** 网页内容诱导 Agent 导出客户名单。

**处置：** 停止外发工具、撤销令牌、隔离任务；从 trace 确认恶意内容→工具调用链，评估泄露范围并通知合规；上线数据标记、域名白名单、DLP 和人工确认，回归同类 payload。

**事故 B（副作用重复）：** 超时重试造成重复建单。

**处置：** 暂停写接口并对账，按业务键去重/冲正；修复幂等表、超时边界和 outbox，增加“网络超时后重试”故障注入测试。

**事故 C（费用失控）：** 工具返回超大文档导致 token 与成本飙升。

**处置：** 截断响应、封顶上下文和租户预算，回滚工具版本；增加响应字节、token/任务和费用告警，验证质量无明显回退。

## ⑧ 常见错误回答

- “先找是谁写错了。”——延误止损且无法防止系统性复发。
- “删掉异常日志。”——破坏取证并可能违反合规留存。
- “重启服务就算恢复。”——副作用、数据一致性和根因仍未处理。
- “把重试次数调大。”——常是雪崩放大器，不是可靠性方案。
- “模型供应商负责安全。”——企业仍需自己控制权限、数据、工具和审计。

## ⑨ Java/Python 实现思路

Python（预算与熔断钩子）：

```python
def before_tool(ctx, tool):
    if ctx.kill_switch or ctx.tenant_spend >= ctx.budget:
        raise RuntimeError("tool disabled")
    if tool in {"refund.create", "email.send"} and not ctx.approved:
        raise PermissionError("approval required")
```

Java：用 Spring Cloud CircuitBreaker 快速失败，Resilience4j Bulkhead 隔离；Micrometer 暴露事故指标，Spring Boot Actuator 提供受保护的 kill-switch（写入策略中心并审计）。

## ⑩ 权衡与最佳实践

- 自动熔断可能误伤正常流量；设置最小样本、冷却时间和人工复核，恢复采用渐进放量。
- 全量审计利于追责但有隐私/成本；采用脱敏摘要+可授权原文，设定保留期限。
- 复杂 runbook 难执行；每个高风险工具一页纸，明确命令、权限、回滚和验收指标。
- 事故数据回灌评测集会暴露敏感信息；先脱敏、分级访问，再用于安全回归。
- 把“可停用、可回滚、可重放、可对账”作为 Agent 上线前的硬门槛。
