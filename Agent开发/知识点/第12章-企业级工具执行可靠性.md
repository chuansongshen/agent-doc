# 第12章：企业级工具执行可靠性

## ① 核心知识点

- **可靠性目标**：工具执行结果可预测、可恢复、可审计；模型不可靠不能成为数据丢失的理由。
- **超时分层**：连接、读取、单次执行、排队、总截止时间分别设置；总截止时间必须传递给下游。
- **错误分类**：参数/权限/业务冲突（不可重试）；网络抖动、429、5xx、租约丢失（可重试）；未知状态（先查询）。
- **重试策略**：指数退避 + 抖动 + 最大次数/总时长；尊重 `Retry-After`，避免客户端和工作流双重重试。
- **幂等**：写操作必须有业务幂等键和唯一约束；幂等记录保存请求哈希、状态和结果引用。
- **并发控制**：按租户/资源限流；写冲突使用版本号或分布式锁，锁必须有租约和续期。
- **降级与补偿**：超时可转异步；部分成功记录补偿任务；不可自动补偿时进入死信队列和人工队列。
- **可观测性**：成功率、P95/P99、重试率、超时率、未知状态、按租户配额和成本。

## ② 原理

一次调用可能经历“已发送但响应丢失”。因此结果状态至少要有：`SUCCESS / FAILED / UNKNOWN / CANCELED`。

```text
请求 → 设置 deadline → 尝试执行
       ├─ 明确成功：落库并返回
       ├─ 明确不可重试：失败并解释
       ├─ 可重试：退避后重试
       └─ 未知状态：查询幂等记录/下游状态，再决定
```

重试次数不能替代总时间预算；每次尝试都带同一幂等键，只有查询动作可在未知状态下安全重复。

## ③ 企业架构

- **Tool Gateway**：统一超时、重试、熔断、限流、幂等和审计。
- **执行队列**：短任务同步；长任务进入队列，使用 `job_id` 查询或事件通知。
- **状态库**：唯一键 `tenant + idempotency_key`；状态迁移采用条件更新，防止并发覆盖。
- **策略中心**：按错误码维护重试白名单、预算和降级动作，可热更新但需版本化。
- **补偿/对账**：每日对账副作用结果；异常自动生成工单，不直接由模型“猜测已完成”。

## ④ 面试标准答案

> 工具可靠性核心是把一次调用设计成可重放的状态机。先分离可重试与不可重试错误，再设置单次和总截止时间；副作用操作使用幂等键、唯一约束和状态查询，避免超时重试造成重复。网关统一限流、熔断、审计和指标，长任务异步化，未知状态进入查询或人工队列，而不是返回“成功”。

## ⑤ 高频追问

**Q：为什么不能只靠重试？** 因为请求可能已经成功但响应丢失，重试会重复副作用。

**Q：熔断后 Agent 做什么？** 返回明确的“暂不可用/稍后查询”，或转异步和人工，不让模型无限改参重试。

**Q：幂等表放什么？** 幂等键、请求哈希、租户、状态、业务结果、过期时间和审计信息；请求哈希不一致应拒绝。

## ⑥ 场景题

**场景：批量给 10 万客户发通知**

拆成可恢复批次（如每批 500 条），每条使用 `campaign_id + customer_id` 幂等键；队列限速，失败按错误码重试；超过预算写入死信队列；最终以供应商回执对账，而不是以提交成功数作为送达数。

## ⑦ 生产事故题

**事故：下游 429，多个 Agent 同时指数重试，队列雪崩。**

- 立即动作：降低并发、暂停非关键任务、读取 `Retry-After`，保护下游。
- 根因：每个客户端自带重试，没有全局预算和租户配额。
- 修复：重试由网关统一；令牌桶限流 + 全局并发上限 + 抖动；按租户隔离队列并设置熔断恢复探测。

## ⑧ 常见错误回答

- “超时就重试，最多三次。”——未区分未知状态和不可重试错误。
- “熔断就是返回空结果。”——必须返回可行动的状态和后续路径。
- “幂等键用时间戳即可。”——时间戳每次不同，无法去重；应由业务请求稳定生成。
- “消息队列保证 exactly-once。”——跨系统通常只能做到至少一次，业务仍需幂等。

## ⑨ Java/Python 实现思路

```python
def call_with_retry(fn, key, deadline, retryable):
    for attempt in range(4):
        if time.monotonic() >= deadline:
            raise TimeoutError("超过总截止时间")
        try:
            return fn(idempotency_key=key, timeout=deadline-time.monotonic())
        except Exception as e:
            if not retryable(e) or attempt == 3:
                raise
            time.sleep(min(2 ** attempt, 8) * random.uniform(.8, 1.2))
```

Java 可用 Resilience4j 实现 Retry/Bulkhead/TimeLimiter，但幂等状态与业务唯一约束仍由数据库负责；不要叠加 SDK 与网关两套重试。

## ⑩ 权衡与最佳实践

- 关键写操作优先“至少一次 + 幂等”，不要追求跨系统伪 exactly-once。
- 重试预算按请求总时限计算；429/5xx 才重试，4xx 参数错误快速失败。
- 把副作用调用封装成可查询状态机；未知状态不得自动补偿。
- 长任务异步化并支持取消、心跳、断点续跑；死信队列必须有人负责。
- 以真实故障演练验证超时、重复提交、进程崩溃和下游恢复。
