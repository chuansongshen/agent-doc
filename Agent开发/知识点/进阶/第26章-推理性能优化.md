# 第26章：推理性能优化

## ① 核心知识点

- 指标分解：TTFT（首 token 时间）衡量排队+Prefill；TPOT/ITL（每输出 token 间隔）衡量 Decode；吞吐用 output tokens/s；同时看 P95/P99 和 GPU 利用率。
- Continuous batching（迭代级批处理）让新请求加入正在解码的批次，减少等待和 GPU 空转；需公平调度，避免长请求饿死短请求。
- KV Cache 保存注意力键值，显著减少重复计算但占显存；Prefix Cache 复用相同前缀，适合固定系统提示和长文档。
- PagedAttention 以固定块管理 KV，降低碎片并提高并发；块大小、上下文长度和并发上限直接影响显存。
- vLLM 提供 PagedAttention、连续批处理、Prefix Cache、量化和投机解码；TensorRT-LLM 提供 in-flight batching、paged attention、量化和多 GPU 优化。
- 量化（INT8/INT4/FP8 等）节省显存、提升吞吐，代价是精度和算子兼容；投机解码用小模型提议、主模型并行验证，收益依赖接受率。
- GPU 隔离：按模型/租户分池，设置显存水位、并发和 MIG/容器资源，避免单模型 OOM 影响全局。

## ② 原理

- 总时延近似 `排队 + Prefill + Decode`；TTFT 主要受排队/输入 token，TPOT 主要受 Decode 和 KV 访存。
- 计算密集的 Prefill 与内存带宽受限的 Decode 特性不同；可按阶段拆分实例（prefill/decode disaggregation）并用队列传递 KV 或请求状态。
- 连续批处理在每个迭代步重新组批，短请求完成后立即退出；调度器以 token budget 控制显存和公平性。
- KV Cache 显存约与层数×头数×序列长度×每元素字节数成正比；前缀共享和分页减少重复/碎片，但缓存命中必须绑定模型、LoRA、租户和权限。
- 量化需校准数据和回归集；权重、激活、KV 可分别量化，优先选择硬件支持的 kernel，并监控异常输出。
- 投机解码速度取决于草稿模型接受率和验证并行度；低接受率或高并发下可能无收益，应通过 A/B 压测决定。
- GPU 隔离通过 requests/limits、节点标签、亲和性、MIG 或独立队列实现；CPU tokenizer、网络和 PCIe 也可能成为瓶颈。

## ③ 企业架构

```text
请求网关（限流/优先级） → Scheduler（continuous batching）
                         ├→ Prefill GPU 池
                         └→ Decode GPU 池（KV/Prefix Cache）
                                   ↓
              vLLM 或 TensorRT-LLM → 多模型/多精度实例
GPU 监控（显存、利用率、TTFT、TPOT、tokens/s）→ 自动扩缩与告警
```

- 固定系统提示和工具 schema 放前缀前部，提高 Prefix Cache 命中；动态用户内容置后。
- 入口按输入/输出 token 估算资源，设置 `max_model_len、max_num_seqs、max_num_batched_tokens` 等硬上限。
- 不同模型和量化精度使用独立 GPU 池；高峰优先级队列保障交互请求，批处理任务可降级或延后。
- 通过 Prometheus/OTel 采集 TTFT、TPOT、队列时长、缓存命中、OOM、拒绝和成本；发布前固定 workload 压测。
- 多实例共享模型权重可用只读缓存，但 KV/Prefix Cache 按租户和版本隔离，避免数据串扰。

## ④ 面试标准答案

> 我先把时延拆成排队、Prefill 和 Decode，分别测 TTFT、TPOT、P95/P99 及 output tokens/s。服务层采用连续批处理和有界 token budget，vLLM 或 TensorRT-LLM 管理 Paged KV Cache；固定前缀启用 Prefix Cache，按硬件选择 INT8/INT4/FP8 量化，必要时用投机解码。模型按精度和租户分 GPU 池，设置显存/并发上限与优先级。所有优化先在代表性负载上 A/B，质量、安全和成本不回退才上线。

## ⑤ 高频追问

- **TTFT 高但 TPOT 正常说明什么？** 多半是排队或 Prefill 瓶颈；看队列时长和输入 token，再调批大小或拆分阶段。
- **为什么 GPU 利用率高仍然慢？** 可能是显存带宽、KV 访存、CPU tokenizer 或网络瓶颈，需分阶段 profile。
- **Prefix Cache 会泄露数据吗？** 可能；缓存键必须含模型/租户/权限摘要，禁止跨租户共享敏感前缀。
- **量化一定更快吗？** 不一定，取决于 kernel 和 batch；先测端到端时延、质量和能耗。
- **投机解码何时关闭？** 接受率低、草稿模型开销大或输出质量/稳定性不达标时关闭。

## ⑥ 场景题

**场景：** 企业助手固定 4k token 系统提示，峰值并发 300，TTFT 目标 1 秒。

**解法：** 将固定提示置于前缀并启用 Prefix Cache；入口限制最大输入和并发，连续批处理按 token budget 调度；交互请求独立高优先级 GPU 池，长报告异步；压测不同 batch/块大小，确认缓存命中率、TTFT P95 和答案一致性。

## ⑦ 生产事故题

**事故：** 开启 INT4 后吞吐提升，但代码 Agent 误删文件比例上升。

**排查与修复：** 对比量化前后安全评测和工具轨迹，确认量化导致指令遵循下降而非工具 bug；立即将高风险工具路由 FP16/FP8 并要求人工确认，回滚 INT4；补充量化专属安全回归和按任务风险路由，重新评估成本收益。

## ⑧ 常见错误回答

- “把 batch 调到最大吞吐就最高。”——会放大 TTFT、显存压力和长尾。
- “GPU 利用率 100% 说明没有优化空间。”——可能是低效 kernel 或带宽受限。
- “KV Cache 越大越好。”——缓存占满会 OOM，应有水位、淘汰和租户隔离。
- “量化只影响模型大小。”——还会影响精度、拒答和算子兼容。
- “投机解码必然 2 倍加速。”——收益依赖接受率、负载和实现，需实测。

## ⑨ Java/Python 实现思路

vLLM 启动示例（先用压测验证参数）：

```bash
vllm serve <model> \
  --enable-prefix-caching \
  --max-model-len 8192 \
  --max-num-seqs 64 \
  --gpu-memory-utilization 0.90
```

Python 客户端记录端到端指标；Java 服务通过 HTTP 调用推理服务，使用 Micrometer 统计 `ttft_ms、tpot_ms、output_tokens、queue_ms`，按租户设置并发信号量。TensorRT-LLM 场景由 Triton 管理模型仓和动态/in-flight batching。

## ⑩ 权衡与最佳实践

- 连续批处理提升吞吐但增加调度复杂度；交互与离线任务分池，分别设 token budget。
- Prefix Cache 节省 Prefill 计算但占显存并有隐私边界；只缓存稳定、无敏感的公共前缀。
- 量化降低成本却可能损失质量；按模型和任务分级，保留高风险 FP16/FP8 回退。
- PagedAttention/大 KV Cache 提高并发但放大显存争用；设置最大上下文、缓存水位和 OOM 降级。
- 每次优化同时验收 TTFT、TPOT、吞吐、质量、安全、成本和能耗，避免只追单一 benchmark。
