# 第25章：部署与发布

## ① 核心知识点

- 镜像不可变：Dockerfile 多阶段构建、非 root、最小基础镜像、漏洞扫描，生产按 digest 而非 `latest` 部署。
- Kubernetes：Deployment 管理无状态 API/Worker，ConfigMap/Secret 外置配置，探针、资源 requests/limits、PDB 保证可用。
- 发布策略：滚动更新适合常规版本；金丝雀按流量/租户逐步放量；蓝绿保留两套环境，切换快但资源翻倍。
- Agent 版本不只是一份代码：Prompt、模型、Embedding、检索索引、Workflow、工具 schema 都需独立版本和兼容矩阵。
- 灰度门禁：离线评测→预生产回放→小流量→逐步扩大；同时观察成功率、P95、成本、安全违规和业务指标。
- 回滚与灾备：代码/配置/模型/索引可回滚，状态库备份与恢复演练，明确 RPO/RTO 和人工接管路径。

## ② 原理

- 滚动更新用 `maxSurge` 控制额外 Pod、`maxUnavailable` 控制不可用数量；readiness 未通过的 Pod 不接流量。
- 金丝雀需要流量切分和分析指标；自动晋级/回滚依赖窗口、最小样本和阈值，不能只看健康探针。
- 蓝绿先启动 Green 并做迁移/冒烟，切换 Service 后保留 Blue 观察窗口；数据库采用 expand-contract，避免旧版本读不到新字段。
- 无状态 Worker 通过队列领取任务，checkpoint 和幂等键放外部存储；发布期间优雅终止，未完成任务可重投。
- Prompt/模型/Embedding/Workflow 灰度都带 `version`，同一任务固定版本；Embedding 索引切换采用双写/双读和回滚标记。
- 灾备指标：RPO（可接受数据丢失时间）、RTO（恢复目标时间）；备份必须定期做恢复而不是只看“备份成功”。

## ③ 企业架构

```text
源码/Prompt/模型/索引/Workflow → CI（测试、评测、SBOM、签名）
                                  ↓ 制品仓库（digest）
环境编排（Helm/Kustomize/Argo） → K8s Deployment/Worker
          ↓ Service/Ingress 流量切分（金丝雀/蓝绿）
          ↓ OTel/Prometheus 质量门禁 → 晋级或回滚
状态库、队列、对象存储 ← 备份/跨区复制 ← 灾备演练
```

- API 与 Worker 分离部署，Worker 按队列长度扩缩，发布时设置 `preStop` 和宽限期。
- 运行时配置通过版本化配置中心下发；Secret 由密钥管理服务注入，禁止写入镜像和日志。
- 每次发布生成 SBOM、镜像签名、Prompt/模型清单和迁移脚本，审批记录可追溯。
- 灰度按租户/地域/流量哈希保持一致，避免同一会话在版本间漂移；高风险租户默认留在稳定版。
- 备份状态库、向量索引和对象存储，记录恢复顺序与依赖，定期演练跨区切换。

## ④ 面试标准答案

> 我把部署制品定义为代码、镜像、Prompt、模型、Embedding、Workflow 和工具 schema 的版本集合。API/Worker 无状态化，状态和队列外置；Kubernetes 通过 Deployment、探针和资源限制保证滚动更新。高风险变更采用金丝雀或蓝绿，按租户固定流量并用成功率、P95、成本和安全指标自动门禁。每个版本可一键回滚，数据库用 expand-contract，状态库和索引有备份及恢复演练，明确 RPO/RTO。

## ⑤ 高频追问

- **Prompt 改动需要发布吗？** 需要，Prompt 是运行时制品，应版本化、评测、灰度和回滚。
- **为什么 Worker 要无状态？** 便于扩缩和滚动发布；执行事实放 checkpoint/队列，避免 Pod 重启丢任务。
- **滚动、金丝雀、蓝绿怎么选？** 低风险兼容变更滚动；模型/策略不确定用金丝雀；需瞬时切换或数据库兼容性复杂时蓝绿。
- **模型回滚是否立刻生效？** 新任务可立即固定旧版本；已运行任务按 checkpoint 版本继续，避免跨模型状态不一致。
- **灾备只备份数据库够吗？** 不够，需同时备份对象、索引、配置、密钥引用和恢复脚本。

## ⑥ 场景题

**场景：** 新 Embedding 模型提升离线召回，但索引重建需 6 小时，不能停服。

**解法：** 新旧索引并行构建并双写；查询按租户灰度双读比较召回和延迟；达到门禁后切换别名，保留旧索引观察窗口；异常只需切回别名，确认稳定后再清理旧索引。

## ⑦ 生产事故题

**事故：** Prompt 灰度未固定会话版本，用户在同一任务中看到前后矛盾的工具参数。

**排查与修复：** trace 显示同一 `task_id` 命中了两个 Prompt 版本；立即停止灰度、固定任务版本并回滚；将 `prompt_version/model_version/workflow_version` 写入 checkpoint，路由按任务哈希固定，新增跨版本会话回放测试。

## ⑧ 常见错误回答

- “镜像打个新标签就能回滚。”——标签可被覆盖，必须使用 digest 和制品清单。
- “readiness 通过就代表 Agent 正常。”——只证明进程可接流量，不代表模型质量和工具链路。
- “金丝雀只看 5xx。”——还应看业务成功率、成本、安全和长尾延迟。
- “数据库迁移和应用一起改最简单。”——发布失败时旧版本可能无法读取新结构。
- “备份成功日志就是灾备完成。”——必须实测恢复耗时和数据完整性。

## ⑨ Java/Python 实现思路

Kubernetes Deployment 最小片段：

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate: {maxSurge: 25%, maxUnavailable: 0}
  template:
    spec:
      containers:
      - name: agent-worker
        image: registry.example/agent@sha256:<digest>
        readinessProbe: {httpGet: {path: /ready, port: 8080}}
        resources: {requests: {cpu: "500m", memory: "1Gi"}, limits: {memory: "2Gi"}}
```

Java：Spring Boot Actuator 暴露 `/ready` 与 `/live`，优雅停机等待队列任务；Argo Rollouts/Service Mesh 按权重切流，Prometheus AnalysisRun 达标才晋级。Python Worker 在 `SIGTERM` 停止取新任务并提交 checkpoint。

## ⑩ 权衡与最佳实践

- 金丝雀降低爆炸半径但需要流量治理和足够样本；无法切流时用按租户路由和影子流量。
- 蓝绿回滚快但成本约翻倍；只对高风险模型/工作流使用，普通代码采用滚动更新。
- 制品越多越难管理；建立兼容矩阵和过期策略，保留最近可恢复版本而非无限堆积。
- 自动回滚避免人工延迟，也可能误判低流量；设置最小样本、冷却和人工复核。
- 上线前必须演练：回滚、队列重放、索引切换、跨区恢复，并记录实测 RPO/RTO。
