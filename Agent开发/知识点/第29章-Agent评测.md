# 第29章：Agent Evaluation

## ① 核心知识点

- 评测对象是完整任务闭环，而非只看文本：目标完成、事实正确、引用有据、工具选择/参数、流程合规、安全、时延和成本。
- 数据集分层：正常/边界/对抗；按租户、语言、业务类型和风险等级覆盖，保留不可公开的线上样本。
- 三类评测：离线回放（发布门禁）、在线监控（真实分布）、人工抽检（校准自动评分）。
- 指标示例：任务成功率、工具调用准确率、参数错误率、事实/引用准确率、拒答安全率、P95 时延、每任务成本、人工升级率。
- LLM-as-a-judge 必须有评分量表、盲测、与人工的一致性（如 Cohen κ）和偏差监控。
- 任何提示、模型、检索器、工具或策略变更都要关联版本并可重放。

## ② 原理

- 先定义“完成”：可验证断言/业务状态，而不是“看起来不错”。每条样本包含输入、期望动作、允许工具、验收条件。
- 任务成功率 (S=成功任务数/总任务数)；工具参数准确率 (A=合法调用数/调用总数)；安全违规率 (V=违规任务数/任务总数)。
- 事实评测可拆为检索召回率、引用精确率、答案支持率；对数值业务使用程序化断言，避免只依赖语言模型裁判。
- 置信区间：对比例指标报告 95% 区间；小样本不做过度结论，可用分层 bootstrap。
- 线上分流：固定 5% 对照/95% 候选，按租户随机且保持任务完整；出现安全或 SLO 回退立即停止。
- 评测流水线：样本库→运行器（固定温度/种子）→规则/模型裁判→统计报告→门禁与回滚。

## ③ 企业架构

```text
样本仓库（脱敏、版本） → Eval Runner → Agent 沙箱/录制回放
                                  ├─规则断言/SQL 校验
                                  ├─LLM Judge（盲评）
                                  └─人工复核抽样
        ↓ 指标仓库/质量看板 ← 线上 trace 与反馈
        ↓ CI 门禁、灰度、自动回滚
```

- 评测环境锁定模型快照、提示版本、检索索引和工具桩；真实写操作使用沙箱或录制结果。
- 质量门禁示例：核心任务成功率不低于基线 -1 个百分点，安全违规率为 0，高风险参数错误率 <0.1%。
- 看板按场景、租户、模型、版本切片，展示样本量和置信区间，避免平均数掩盖长尾。
- 反馈按钮、人工改写和事故样本自动进入待标注队列；标注指南和双人复核保证一致性。

## ④ 面试标准答案

> 我先把业务“完成”定义成可验证状态，再建立分层黄金集。离线评测同时看成功率、事实/引用、工具调用、安全、P95 时延和成本；程序化断言优先，LLM 裁判只处理开放式质量，并用人工盲评校准一致性。所有运行记录模型、提示、检索和工具版本，CI 用置信区间和回归阈值门禁，线上用小流量对照与异常自动回滚。事故和用户反馈持续回灌数据集，形成闭环。

## ⑤ 高频追问

- **为什么不能只用 BLEU/ROUGE？** 它们衡量字面相似，无法验证任务状态、工具副作用和安全。
- **LLM 裁判可靠吗？** 需固定量表、盲测、人工校准和偏差检测；关键结论用程序化规则。
- **如何评测多步 Agent？** 对最终结果和每一步轨迹分别评分，定位首次错误，而非只看最终文本。
- **线上指标下降多少才回滚？** 预先定义最小样本和置信阈值，例如成功率下降>2 个百分点且 95% 区间不重叠。
- **如何避免测试集泄露？** 留出私有集、按时间切分并轮换对抗样本，限制评测日志访问。

## ⑥ 场景题

**场景：** 报销 Agent 更换模型，离线平均分提升，但财务投诉增加。

**解法：** 按场景切片发现“发票税额校验”长尾下降；补充真实边界样本，用程序化金额/税率断言和工具轨迹评分；灰度限制在低风险租户，设置高风险任务自动回滚，确认置信区间后再扩大流量。

## ⑦ 生产事故题

**事故：** 评测看板显示成功率 98%，上线后出现大量错误退款。

**排查：** 发现测试工具桩总是返回成功，未验证幂等和金额边界；指标只看最终文本。立即关闭退款工具、人工复核未完成任务；重建包含真实失败和副作用模拟的沙箱，增加“工具结果真实性、参数合法性、重复调用”断言，门禁改为高风险违规率=0。

## ⑧ 常见错误回答

- “跑 100 条样本，平均分高就够了。”——样本无分层且无置信度。
- “全部交给 GPT 评分。”——裁判偏差和不可解释性会掩盖业务错误。
- “只评最终答案。”——无法定位工具选择、权限和中间状态问题。
- “线上用户反馈不适合做评测。”——脱敏后恰是最有价值的分布数据。
- “指标越多越好。”——应围绕 SLO 选少数可行动指标，避免噪声。

## ⑨ Java/Python 实现思路

Python（程序化门禁示例）：

```python
def evaluate(case, result):
    ok = result.status == case.expected_status
    tool_ok = all(c in case.allowed_tools for c in result.tool_calls)
    safety_ok = not result.policy_violation
    return {"success": ok and tool_ok, "safety": safety_ok,
            "latency_ms": result.latency_ms, "cost": result.cost}

scores = [evaluate(c, run(c)) for c in dataset]
assert sum(x["safety"] for x in scores) == len(scores)  # 高风险门禁
```

Java：JUnit 参数化测试加载 JSONL 用例；AssertJ 校验结构化状态，Micrometer 记录指标；LLM 裁判异步执行并把评分量表、模型版本和原始证据写入评测库。

## ⑩ 权衡与最佳实践

- 黄金集越大成本越高；核心高风险场景全量，低风险场景分层抽样并持续轮换。
- 自动裁判便宜快速但有偏差；用 5%～10% 人工盲评校准，发现 κ 下降就暂停自动门禁。
- 固定温度便于回归，生产仍有随机性；对关键样本重复运行 3 次观察方差。
- 质量、时延、成本不可只优化单项；采用加权目标并为安全/SLO 设置硬约束。
- 评测结果必须可重放、可追责、可回滚，任何“模型升级”都视为代码变更管理。
