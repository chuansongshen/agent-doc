# 第22章：流式输出与长任务

## ① 核心知识点

- 流式输出：服务端持续发送增量事件，降低首字节/首 token 延迟（TTFT），但不改变最终结果语义。
- 事件模型：`run_started`、`message_delta`、`tool_call`、`tool_result`、`progress`、`run_completed`、`run_failed`、`heartbeat`。
- 传输选择：SSE 适合服务端到客户端的单向文本流；WebSocket 适合双向控制（暂停、取消、追问）；长任务结果应通过任务 API 查询。
- 长任务：提交即返回 `task_id`，后台 worker 执行；状态至少有 queued/running/waiting/succeeded/failed/cancelled。
- 可靠性：幂等键、持久化 checkpoint、事件序号、断线重连、超时、取消、死信和人工接管。
- 关键指标：TTFT、流中断率、事件重放率、任务成功率、端到端时延 P50/P95、取消生效率。

## ② 原理

- SSE 以 `text/event-stream` 按事件分帧，客户端可用 `Last-Event-ID` 从上次序号继续；代理层需关闭缓冲并定期心跳。
- 事件至少一次投递是常见取舍：消费者按 `event_id` 去重，服务端保存短期事件日志，避免重复渲染。
- Agent 运行循环：模型增量 → 聚合器 → 事件总线；工具调用期间发送 progress，工具完成后写入 checkpoint 再继续推理。
- 长任务状态机：`queued→running→waiting(人工/外部回调)→running→succeeded|failed|cancelled`；状态转换必须原子且带版本号。
- 断点续跑保存“已完成步骤、输入摘要、工具结果引用、重试次数、运行版本”，不要只保存聊天全文。
- 背压通过有界队列、丢弃低优先级进度事件和限速发送实现；最终状态事件不可丢。

## ③ 企业架构

```text
客户端 ──API Gateway──> Task API ──> 任务库/幂等表
   │                         └────> 消息队列 ──> Agent Worker
   │                                             ├─模型/工具
   └─SSE/WebSocket 网关 <──事件总线<── checkpoint/事件库
```

- Task API 只负责鉴权、幂等和返回 `task_id`；Worker 无状态化，状态放数据库/对象存储。
- 事件总线按 `task_id` 分区保证顺序；SSE 网关支持重连、租户限流和连接数上限。
- Checkpoint 与业务副作用同事务或采用 outbox；外部回调使用签名、过期时间和幂等键。
- 取消请求写入 cancel 标记，Worker 在模型调用和工具边界检查；不可中断的工具需设置补偿动作。
- 监控按任务、租户、模型、工具维度聚合，日志脱敏并关联 `trace_id`。

## ④ 面试标准答案

> 流式输出解决的是感知延迟，长任务解决的是执行时长和连接可靠性。我的做法是提交任务立即返回 `task_id`，后台按状态机执行并持久化 checkpoint；前端通过 SSE/WebSocket 接收有序事件，断线携带最后事件号重放。所有工具调用使用幂等键，最终结果以任务库为准，流只做实时展示。超时、重试、取消、死信和人工接管都由运行时控制，而不是交给模型。

## ⑤ 高频追问

- **SSE 断线会丢数据吗？** 会，除非保存事件序号并支持重放；客户端去重后再渲染。
- **为什么不用一直保持 HTTP？** 长任务可能超过网关超时且占用连接；改为异步任务，连接只订阅事件。
- **如何避免工具重复执行？** `idempotency_key = task_id + step_id`，服务端记录执行结果并在重试时返回旧结果。
- **流式 token 能否直接落库？** 不建议；增量仅缓存，收到完成事件后写最终消息，必要时异步归档。
- **如何判断任务卡死？** 心跳超时 + checkpoint 未推进；先重试可重入步骤，超过阈值转人工。

## ⑥ 场景题

**场景：** 生成一份含 200 个数据源的审计报告，预计 10 分钟，用户可能刷新页面。

**解法：** 提交返回任务号；每个数据源为可重试步骤，完成即 checkpoint；进度事件只保留最近 N 条；刷新后先查询任务状态，再从事件号续接；报告写对象存储并返回下载地址；失败步骤汇总后允许“仅重跑失败项”。

## ⑦ 生产事故题

**事故：** 代理升级后 SSE 客户端频繁显示重复段落，任务实际只执行一次。

**排查与修复：** 对比 `event_id` 发现网关重试导致重复投递；客户端未去重且服务端无重放边界。立即按事件号去重、增加 `Last-Event-ID` 重放窗口和网关禁用缓冲；补充重复投递率、断线率告警，并回放历史任务验证最终结果一致。

## ⑧ 常见错误回答

- “把模型输出逐字转发就是流式架构。”——忽略事件协议、断线、顺序和错误。
- “长任务把 HTTP 超时调大即可。”——连接仍受代理、浏览器和扩缩容影响。
- “重试越多越可靠。”——无幂等会重复扣款、发信或写库。
- “进度百分比由模型估算。”——应由已完成步骤/总步骤计算，模型只提供状态说明。
- “取消就是关闭前端连接。”——关闭连接不等于停止后台副作用。

## ⑨ Java/Python 实现思路

Python（FastAPI SSE，最小示例）：

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import asyncio, json

app = FastAPI()

async def events(task_id: str, after: int = 0):
    for e in load_events(task_id, after):       # 按序号读取并去重
        yield f"id: {e['id']}\ndata: {json.dumps(e, ensure_ascii=False)}\n\n"
        await asyncio.sleep(0)

@app.get('/tasks/{task_id}/events')
async def stream(task_id: str, last_event_id: int = 0):
    return StreamingResponse(events(task_id, last_event_id),
                             media_type='text/event-stream',
                             headers={'Cache-Control': 'no-cache', 'X-Accel-Buffering': 'no'})
```

Java 思路：Spring WebFlux `Flux<ServerSentEvent<Event>>` 输出 SSE；任务执行使用消息队列消费者，checkpoint 采用数据库乐观锁（`version` 条件更新），重试由队列重投和幂等表控制。

## ⑩ 权衡与最佳实践

- SSE 简单、可观测、穿透代理好；需要双向控制时再选 WebSocket，避免无谓复杂度。
- 事件日志保留 1～24 小时即可覆盖重连窗口；长期审计存最终结果和摘要。
- 进度事件可丢、状态事件不可丢；队列必须有界并对租户隔离，防止单任务占满连接。
- 模型调用设置较短超时，工具按风险分级：读操作自动重试，写操作人工确认或事务补偿。
- 发布新运行时保留旧版本可恢复，checkpoint 中记录 `workflow_version`。
